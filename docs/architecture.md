# Architecture

BrutalKit is a small CSS library, not a component framework. Keep the architecture explicit and easy to consume.

## Runtime layers

1. **Stylesheet:** `src/brutal.css` is the source of truth for component styles and design tokens.
2. **Optional behavior:** `src/brutal.js` progressively enhances tabs and native dialogs. CSS-only components remain usable without it.
3. **Distribution:** `dist/brutal.css` and `dist/brutal.min.css` are generated by `scripts/build.mjs`.
4. **Metadata:** `components.json` inventories public classes and behavioral contracts; its shape is defined by `schemas/components.schema.json`.
5. **Documentation:** `README.md`, `docs.html`, and `docs/recipes.md` describe the public API.

## Visual language

The default theme follows Cramio's design system: paper `#f7f6f2`, ink navy `#20233b`, purple primary `#7055d9`, amber `#ffc93c`, and restrained sky, peach, mint, and lilac accents. DM Sans is the body face and Manrope is the display face, with system fallbacks. Components use medium corner radii and offset ink shadows. Keep the visual language consistent, but do not add decorative motion or brand-specific assets to the core library.

The public design tokens live in `src/brutal.css`. Keep demo and documentation styles aligned with those defaults without leaking demo-only selectors into the distributable stylesheet.

## Dependency policy

- No runtime dependencies. Prefer browser-native HTML, CSS, and JavaScript.
- Do not add a framework abstraction or component registry runtime.
- Development dependencies need a clear build, test, or development purpose.
- Avoid polyfills unless a documented browser-support requirement justifies them.

## Performance contract

- Do not load JavaScript for CSS-only components.
- Avoid layout thrashing, polling, global observers, and per-element listeners when event delegation is sufficient.
- Prefer CSS transitions, honor reduced motion, and keep selectors scoped to BrutalKit classes/data attributes.
- CI enforces conservative file-size ceilings. Change them only with measured justification.

## Adding a component

1. Confirm native HTML or an existing primitive cannot solve the use case.
2. Define semantic markup and accessibility contracts first.
3. Add styles to `src/brutal.css` using existing tokens.
4. Add optional JS only when native HTML/CSS is insufficient.
5. Update `components.json`, docs, and regression tests.
6. Run build, tests, manifest validation, and size checks.

## Boundaries

- Never hand-edit `dist/`; regenerate it.
- Keep demo-site CSS out of the library stylesheet.
- Do not add global resets or broad element selectors.
- Do not promise framework-specific components. The API is HTML + CSS with optional vanilla JS.
- Do not document npm installation unless publication and public package metadata are verified.
